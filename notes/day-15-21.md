# Day 15–21 — Evaluation pipeline

## Done
- **Rubric v1** (`src/lib/eval/rubric.ts`): 5 dims × 1–5, with 1/3/5 anchors per dim so scoring is calibrated
- **Judge** (`src/lib/eval/judge.ts`): LLM-as-judge using `generateObject` against `RubricScores` schema; injects ground truth when scenario is known; temp=0
- **`POST /api/evaluate`**: judges a single analysis row, persists to `evaluations` table
- **`scripts/run-evals.ts`** + `npm run evals:run`: batch runner for 5 scenarios × 2 prompt versions = 10 generations + 10 judgements; prints summary table to terminal
- **`/evals` dashboard**: aggregates by `prompt_version`, shows per-dim averages + individual eval rows with badges
- **`<EvaluateButton />`** on incident detail page for on-demand scoring of a specific analysis
- **`EVALUATION.md`** methodology doc — for the README, the blog post, and any interview where someone asks "how do you know your prompt works?"

## Decisions
- **Judge model = same family as analyzer** (DeepSeek for both). Cost-effective. The risk is optimistic bias; called this out in EVALUATION.md "Limitations" with a planned human-vs-judge agreement study.
- **Rubric anchors at 1/3/5 only** (not all 5 levels). Forces the judge to pick a clear position rather than waffle at 4. Two anchored extremes + a midpoint covers it.
- **Eval table doesn't store the analysis again** — just `analysis_id` FK. Single source of truth for the response, allows re-judging with rubric v2 later.
- **No per-scenario repeats yet** — listed as roadmap item. Doing it would 3x the API spend; acceptable trade for a side project.

## What this unlocks for the project narrative
- A concrete "v1 → v2 improved 2.8 → 4.3" number for the resume, instead of "iterated on the prompt"
- A repeatable methodology that scales to v3, v4 without re-doing the work
- The eval pipeline IS the moat. Anyone can write a prompt; few set up the loop to know if it's good.
